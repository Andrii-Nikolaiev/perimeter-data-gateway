# Perimeter Data Gateway — Требования к продукту v0.1

Предшествует `perimeter-data-gateway-spec-v0.1.md` (технической архитектурной
спеке). Этот документ отвечает на вопрос «что мы строим, для кого и зачем» —
до того, как появится хоть один интерфейс или класс.

## 1. Обзор продукта
- Рабочее название: **Perimeter Data Gateway (PDG)**.
- Назначение: self-hosted шлюз, дающий AI-агентам и другим внутренним
  сервисам контролируемый, аудируемый, read-only доступ к части существующей
  корпоративной БД — без выдачи прямых credentials к базе.
- Статус: задуман как самостоятельный бесплатный, self-hosted,
  source-available проект — не просто артефакт под одну вакансию. Первая
  версия делается параллельно с откликом на позицию Senior .NET Developer и
  одновременно служит настоящим архитектурным упражнением, но продукт должен
  оправдывать себя независимо от этого происхождения.

## 2. Проблема, которую решаем
- Корпоративные данные уже лежат в базах, которые не проектировались под
  этот продукт и не будут под него переделываться.
- AI-агенты и внутренние инструменты не должны получать прямые credentials к
  БД или неограниченный SQL-доступ.
- Доступ должен ограничиваться по полю, по строке и по тому, кто спрашивает
  — и от чьего имени.
- Каждое решение о доступе, разрешение или отказ, должно быть привязано к
  конкретному человеку и конкретному агенту и залогировано.
- Данные не должны покидать инфраструктуру заказчика.

## 3. Целевая аудитория
- Компания с собственной on-premise или self-hosted реляционной БД, которая
  хочет дать AI-агенту или внутреннему инструменту безопасный, чётко
  определённый срез данных, не открывая саму базу.
- Конкретно: небольшие/средние компании с собственной БД; внутренние
  platform/IT-команды; разработчики внутреннего AI-ассистента; системные
  интеграторы; архитекторы, которым нужен reference implementation шлюза
  governance для AI-to-data доступа.
- Две разные роли с самого начала: **администратор**, разворачивающий PDG и
  определяющий Published Resources и policy, и **вызывающая сторона**
  (AI-агент или сервис), потребляющая API. v0.1 сохраняет это разделение
  даже в упрощённом виде.

## 4. Сценарии использования
- **A — AI-помощник продаж.** Отвечает на вопросы о продажах из
  `SalesSummary`, в рамках разрешённых стран вызывающей стороны.
  *(реализуется полностью в v0.1)*
- **B — Support AI.** Видит то, что нужно для ответа клиенту, но не
  финансовые детали.
- **C — Management analytics.** Руководитель через AI запрашивает
  агрегированные цифры.
- **D — Не-AI внутренний сервис.** Любое внутреннее приложение, не только
  AI-агент, может использовать PDG как контролируемый шлюз доступа к данным.

  В v0.1 строится только A. B–D существуют, чтобы архитектура случайно не
  стала AI-специфичной — см. заметку про нейминг в §10.

## 5. Почему готовая корпоративная база данных
- Мы не проектируем собственную схему. Продукт должен работать против
  существующей, чужой базы — не подогнанной под удобство PDG.
- Известная публичная база позволяет любому воспроизвести демо без доступа к
  данным реального клиента.

## 6. Почему Chinook
Сравнение с AdventureWorks и Pagila по критериям: лицензия, доступность,
понятность предметной области, размер, наличие PII-подобных колонок,
поддержка PostgreSQL, поддержка SQL Server, трудоёмкость Docker-развёртывания.

- **Chinook** — лицензия MIT; единственная из трёх с реально поддерживаемой,
  активно затулленной поддержкой SQL Server, Oracle, MySQL, PostgreSQL,
  SQLite и DB2 из одной схемы (проверено: апстрим-репозиторий собирает и
  тестирует все варианты через `dotnet build` + `docker compose`). Именно
  эта кросс-СУБД реальность позволяет позже не просто заявить, а
  продемонстрировать тезис архитектурной спеки о storage-agnostic
  Application-слое.
- **AdventureWorks** — богаче и «корпоративнее» на вид, но SQL-Server-native;
  ослабляет кросс-СУБД историю.
- **Pagila** — Postgres-native с сильными Postgres-специфичными фичами, но
  предметная область (прокат фильмов) хуже читается как корпоративные данные
  о продажах.

## 7. Почему PostgreSQL первым
- Бесплатен в запуске, дружелюбен к Docker, никакого лицензионного барьера
  для того, кто просто хочет попробовать PDG.
- Зрелые roles/grants/views — используются напрямую для defense-in-depth по
  колонкам/строкам в архитектурной спеке.
- Зрелый, хорошо поддерживаемый .NET-драйвер (Npgsql).
- **PostgreSQL — первый поддерживаемый provider, а не архитектурное
  ограничение.** Application-слой не имеет права предполагать
  Postgres-специфичное поведение.

## 8. Почему EF Core — не «выбор под SQL Server»
`.NET + EF Core` рефлекторно читают как `.NET + SQL Server`; стоит явно
проговорить, почему здесь не так.
- EF Core — provider-based ORM, а не ORM исключительно под SQL Server;
  Npgsql EF Core provider зрелый и широко используется.
- Запуск EF Core поверх PostgreSQL с первого дня — само по себе
  демонстрация vendor-independent application logic, а не просто заявление
  в README.
- SQL Server может стать вторым provider позже, не трогая Application-слой.
- Postgres идёт первым не потому, что SQL Server хуже, а потому что это
  снижает порог входа для свободно распространяемого self-hosted продукта.

## 9. Почему две базы данных
- Собственная конфигурация PDG, policy и audit-трейл операционно отделены от
  корпоративных данных, которые они защищают.
- PDG не должен требовать изменения структуры БД клиента.
- Разные credentials, разный уровень прав, разные жизненные циклы —
  корпоративная БД принадлежит клиенту, платформенная БД принадлежит PDG.

## 10. Функциональные требования v0.1
Здесь нет имён интерфейсов или классов — это уровень архитектурной спеки.
- Подключение к одному корпоративному источнику данных.
- Данные отдаются только через определённый Published Resource, никогда
  напрямую из таблиц.
- Аутентификация каждой вызывающей стороны.
- Разделение человека, от имени которого выполняется вызов, и агента/сервиса,
  который его выполняет — см. заметку про нейминг ниже.
- Проверка доступа на уровне ресурса (может ли вызывающая сторона вообще
  использовать этот ресурс).
- Проверка доступа на уровне строк (какие строки внутри ресурса).
- Проверка доступа на уровне колонок (какие поля вообще возвращаются).
- Запись каждого решения о доступе, разрешённого или отклонённого.
- Всё вышеперечисленное доступно только через API — никакого прямого доступа
  к БД для любой вызывающей стороны.

> **Заметка про нейминг для архитектурной спеки:** из-за сценария D (§4) в
> domain-модели вызывающую сторону нельзя называть `AIAgent`. Общий термин
> (например, *delegated actor* / *caller*) сохраняет честность продукта в
> отношении того, чем он на самом деле является — общий шлюз доступа, где AI
> это первый сценарий, а не AI-эксклюзивный инструмент.

## 11. Нефункциональные требования
- Полностью on-premise / self-hosted; никакой обязательной внешней
  cloud-зависимости.
- Запуск через Docker одной командой.
- Secure by default; least privilege на уровне приложения и на уровне БД.
- Каждое решение аудируемо.
- Воспроизводимо на чистой машине.
- Документировано достаточно, чтобы запустить и понять без вопросов автору.

## 12. Чем v0.1 не является
Не LLM и не чатбот · не CRM · не универсальный database proxy · не ETL · не
BI-инструмент · не Identity Provider · не универсальный SQL-over-HTTP
endpoint.

## 13. Дистрибуция *(намеренно сжато для v0.1)*
- Публичный репозиторий на GitHub.
- Лицензия: скорее всего MIT, по аналогии с лицензией самого Chinook и для
  минимизации трения при внедрении — финальная формулировка решается, когда
  v0.1 будет готов.
- Публикация Docker-образа, теги релизов и container registry — решения
  после v0.1, не блокеры для v0.1.

## 14. Продвижение *(намеренно сжато для v0.1)*
- Никакого плана продвижения до появления рабочего v0.1. Внятный README —
  единственный «маркетинг», нужный v0.1. Каналы пересматриваем после того,
  как вертикальный срез заработает end-to-end.

## 15. Критерий полезности
Человек, никогда не слышавший об Андрее или Devart, должен, открыв страницу
на GitHub, подумать: *«Я могу поставить это перед своей PostgreSQL и дать
своему внутреннему AI контролируемый, read-only доступ к части данных»*.
Если репозиторий имеет смысл только после «я сделал это под вакансию» — это
учебное упражнение, что тоже нормально делать, но это не то, что заявлено в
§1, и стоит понимать, какое из двух мы на самом деле строим.
